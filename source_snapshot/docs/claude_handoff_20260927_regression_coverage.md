## Source/route compatibility, not acceptance

For the 68 older-owned rows, base Orc, and stopgap wolf (70 total), the installed `.manifest` files and `tools/homm3_import/homm3_units_manifest.json` exactly name the current installed import's bundle/prefab path and `skinned_mesh` lane. Each has a prefab and `owned_skinned.overrideController` at the corresponding `V:/homm3_unity_work/Assets/CustomUnits/homm3_lab/<labSid>/OwnedSkinned/` path. Of 3,616 installed-manifest asset references, 3,615 still exist in the project. The sole missing asset is `toa_boar_rider/OwnedSkinned/Source/master.glb`. None of those 70 source assets has an mtime newer than its installed bundle. This is useful provenance, not a cryptographic proof that Unity would reproduce the installed mesh/clip/texture bytes. No frozen selection or current `build_out` candidate exists for the 68 no-frozen rows.

UnityPy readback of all 70 installed bundles found 69 with `14.Attack -> Unit_AttackFront` and `15.Skill_1 -> Unit_Mouseover`; the stopgap wolf maps both slots to `Unit_Idle`. The required underlying clips are present for all but two:

- `h3_leprechaun`: the installed bundle **and current Unity source** lack `Unit_ShootFront`, although Core gives it a projectile default attack and a separate melee alternative/counter. Repointing its shot slot to AttackFront without establishing a distinct melee animation would be a silent visual fallback, not the requested fix. A source-backed second clip or explicit game-view decision is required and would leave the simple override-only scope.
- `h3_wolf_rider_upg_alt`: no `Unit_AttackFront` in the stopgap installed bundle, only Idle in the source animations, and its installed manifest references missing `Source/master.glb`. This cannot be made correct by an override remap.

There is also a shared source-contract trap: `Homm3OwnedSkinnedLabBuild.StockMap` currently chooses `Unit_ShootFront` for `15.Skill_1` whenever that clip exists, independent of the Core view. The older `h3_vampire_upg_alt` and `h3_medusa_upg_alt` have **nonprojectile** ability@1 but their current Unity assets contain `Unit_ShootFront.anim`; a blind current-StockMap rerun would play a shot for a melee ability. Candidate-Core view requirements, not clip presence, must drive the exact override; the existing attack-clip validator should fail a wrong mapping. No allowlist or global threshold change is justified.

The existing generic `BuildCustomUnitBundles.BuildFromManifest` can build exact bundle names from a unit SID list after the serialized override is correct. It does not by itself fix existing overrides. `Homm3OwnedSkinnedLabBuild.BuildFromCommandLine` **does** regenerate prefab/clips from the master GLB, potentially promoting new motion/look, and `ship_ingame_candidates.py` rebuilds selected mocap inputs; neither is a proven override-only route for these installed older bytes. I found no current validated remap-only driver. A proper bounded implementation would edit only the existing override controller according to candidate-Core per-SID slot requirements, use a source-asset preservation pin for all other prefab/clip/mesh/texture inputs, build exact manifest bundles, and make the existing candidate-Core attack-clip gate plus payload/probe gates fail closed. This is a proposed method, not an executed or accepted lane.
