## First-Pass Implementation

The approved resource-constrained iteration targets known redundant work, not the contended capture's duration. The owned-skinned map path reuses the final scale and floor-relative pivot offset for fresh clones of the same live template, sizing calibration, parent world basis, initial rotation, and initial skin-weight setting. A cold distinct context retains the original exact `BakeMesh` fit/plant sequence, including the final grounding pass after presentation compatibility setup; only its successfully grounded result is published. Matching later clones avoid those bounds passes while still preparing their own presentation state. No serialized `localBounds`, static presentation-report substitution, disk cache, or alternate asset reader is introduced. Dynamic refresh, battle, and preview paths retain their separate measurement owners. Per-instance native squad, fog, animation, and material state remain separate.

Hero sprite loading creates one deterministic recursive frame index per cold sprite-set load instead of enumerating/sorting for each of its 45 selected frames. It retains the same five idle and forty walking frames, point filtering, clamp wrapping, image decode, and fog behavior. PNG byte transfer uses the installed IL2CPP runtime's managed-array constructor, whose inspected IL allocates a native array and bulk-copies through a span; it replaces the per-byte proxy-write loop. PNG decoding/upload still occurs, so this is not native texture packaging or a persistent decoded cache.

The focused hero fixture compiles and exercises the actual frame-index helper, including canonical selection, duplicate ordering, extra frames, and missing-frame/directory behavior. Hook wiring and bulk-copy selection are source guards, not an in-game integration test. The fixture joins the full-validation build tier with a bounded execution timeout. The existing owned-unit presentation validator also guards cache identity, exact miss ordering, successful post-compat publication, and floor-offset capture/replay; its `--source-only` mode checks these without remeasuring bundles or rewriting the presentation artifact. This is source proof, not a Unity runtime-equivalence test. No bulk asset regeneration, game launch, or performance capture is part of this pass.

Full no-measurement first-use delivery still needs raw unplanted idle-pose minima and asset/pose provenance in the content pipeline. The existing presentation report publishes final planted bounds and is insufficient for that reader. Native async/map-input caching and general donor removal are deferred because the synchronous native consumer and its readiness/lifetime handoff are not established; a just-in-time async wait would not eliminate work.

## Ranked Opportunities

The order reflects identifiable repeated work, architecture, and relevance to first-map loading, not the contended capture's durations or promised seconds saved. Source paths below are under `Heroes of Might & Magic Olden Era Playtest/OfflineUnlockMod/`. The audit's line references describe the pre-optimization source; the First-Pass Implementation section states which work has now been removed. ### Precompute Unit Presentation Measurements

**Source/static finding:** owned-skinned map placement calls `ApplySkinnedAdventureMapVisualScale`, samples the idle pose, and measures rendered bounds. `TryGetBakedSkinWorldBounds` calls `SkinnedMeshRenderer.BakeMesh`, copies the vertex array, and transforms every vertex to accumulate bounds. On the initial calibrated `fitScale:true` route, fitting measures bounds, its feet-alignment call measures again, and the caller aligns feet again after idle setup. Each alignment re-enters bounds measurement. Thus this source path requests three full bounds passes per eligible visual; exact skin count, pose, and other entry routes still need attribution rather than extrapolation. Source: `Homm3ImportVisuals.cs:5150-5179,5342-5365,5396-5449,5625-5640`.

Unity documents that [BakeMesh performs skinning on the CPU regardless of GPU Skinning](https://docs.unity3d.com/6000.0/Documentation/ScriptReference/SkinnedMeshRenderer.BakeMesh.html). Thus an NVMe or a larger shader cache does not remove this class of work.

**Proposed root fix:** deliver validated idle-pose measurements with the immutable unit asset, and apply the resulting scale and grounding transform during placement rather than measuring each clone. Generate per-vertex calculations on the GPU under the repository GPU policy, with a CPU parity reference. Preserve the existing exact posed-geometry definition; serialized `localBounds` is explicitly unsuitable in current source. Record the mesh, controller, sampled pose, orientation, and calibration provenance so stale measurements cannot be silently reused. Presentation-reader changes would follow the existing payload ABI mechanism and validator/build-tier rules, not DLL-hash pinning.

**Value and limits:** useful on the first and later maps; tiny metadata storage compared with meshes. The contended 14.592 s shell checkpoint does not establish representative cost, the share spent on bounds, or a savings estimate. The repeatable source-level measurement work is the reason to investigate this option. Profiling and acceptance of size, facing, grounding, and fog are required before replacing runtime measurement.

### Package Hero Sprites for Native Loading

**Source/static finding:** a new hero sprite set loads five idle facings and forty walk frames. Each `LoadSingleFrame` calls `FindFrameFiles`, which recursively enumerates the directory; each PNG then takes `ReadAllBytes`, a new `Texture2D`, and image decode. The sprite-set dictionary prevents repeated decode for a still-valid in-process key, but not a cold first distinct key. Source: `Homm3HeroMapSpriteHook.cs:41,52,1725-1763,1797-1823,1854-1868,1997-2019,2152-2159`. The route defaults on in `LauncherConfig.cs:327` and is registered at `Plugin.cs:890-894`; that is source configuration, not a timed installed-path proof.

**Proposed root fix:** create an indexed native texture asset/atlas/array package during asset preparation, preserving exact frame timing, alpha, filtering, facing, and fog behavior. Select one declared representation per delivered sprite set, not a silent PNG fallback. Build-time indexing removes repeated discovery; native texture serialization also removes runtime PNG decode. This reduces work even on the first map rather than charging it to startup.

Unity confirms that [LoadImage forces synchronous texture upload](https://docs.unity3d.com/6000.0/Documentation/Manual/LoadingTextureandMeshData-make-compatible.html). Imported textures can qualify for asynchronous upload; skinned/blend-shape meshes have additional restrictions, so an asynchronous asset request does not guarantee asynchronous mesh upload.

**Value and limits:** additional derived disk assets, with format/size chosen by measurement. No current per-hero load timing was found. This does not explain the zero unit disk-frame counter, which instruments a different path.

### Avoid Full Donor Visual Construction

**Source/static finding:** the map hook substitutes a native donor resource path before native load, then builds a donor shell and attaches the owned visual after the native method returns. Donor renderers are subsequently suppressed while presentation/fog behavior is retained. Source: `Homm3ImportUnitViewHook.cs:228-239,250-328` and `Homm3ImportVisuals.cs:1150-1271`.

**Proposed root fix:** register or prepare a native-compatible presentation template containing only required native behavior and the final visual, rather than constructing a complete donor visual to hide it. Own this at the native resource/template boundary. Keep map-squad registration, shader material properties, renderer flags, fog, animation, and facing intact.

**Feasibility boundary:** a lightweight prefix route already skips the native loader for eligible map-array pilots (`Homm3ImportUnitViewHook.cs:217-225`, `Homm3ImportVisuals.cs:1295-1349`). It is not a production solution for the general owned-skinned roster, and does not establish that removing donor components is safe. This is a larger architecture change, to pursue after stage attribution and precomputed presentation metadata.

### Overlap Required Asset Reads and Raise Loading Budgets

**Source/static finding:** map bundles/templates are cached only in process; bundle loading uses synchronous `AssetBundle.LoadFromFile` and assets use synchronous `LoadAsset`. Source: `Homm3ImportVisuals.cs:100-115,7269-7435`. A battle prewarm exists at `7449+`; no map-entry/template prewarm was found in `Homm3ImportVisuals`. Other features have distinct prewarm methods, including minimap textures and town-map billboards; this is not a claim that every map-related asset lacks prewarm.

**Proposed experiment:** derive the exact required asset set, queue Unity-native asynchronous loads early in the existing loading sequence, and await readiness before native consumers require the objects. Do not simply replace a synchronous call with an async call and immediately block on it. Do not move Unity object creation to arbitrary worker threads.

Read current `Application.backgroundLoadingPriority`, `QualitySettings.asyncUploadTimeSlice`, and buffer size before tuning them. No textual override was found in the inspected mod/decomp/logs or `boot.config`, but serialized settings remain unknown. Unity's [background loading priority](https://docs.unity3d.com/6000.0/Documentation/ScriptReference/Application-backgroundLoadingPriority.html) controls main-thread integration budgets, from 4 ms at BelowNormal to 50 ms at High. A loading-only increase could help a throttled asynchronous path; restore the previous settings on completion, cancellation, and failure. This is not a prediction of proportional speedup and does not accelerate arbitrary synchronous map logic.

**Value and limits:** little disk overhead, some transient memory. Potential first-map benefit through overlap or removing throttling. Readiness, cancellation, and memory limits need a single explicit ownership path.

### Prepare Targeted Shader Variants

**Verified recorded environment:** Unity 6 with DirectX 11. Unity documents [ShaderVariantCollection.WarmUp as fully supported on DX11](https://docs.unity3d.com/6000.0/Documentation/ScriptReference/ShaderVariantCollection.WarmUp.html). Do not introduce a DX12-specific experimental pipeline-state solution merely because it exists in Unity 6.

**Proposed experiment:** first determine whether shader creation materially contributes in an uncontended run, then prepare the variants actually used by world terrain, fog, owned unit materials, and custom map presentation. Warm those on the actual GPU in an explicit cache-preparation pass or during genuinely idle menu time, and verify benefit in a fresh process with the driver cache preserved. Preparation costs must be reported separately from normal startup/map waits.

Windows documents [driver support for in-process and automatic disk shader caches](https://learn.microsoft.com/en-us/windows/win32/api/d3d11/ne-d3d11-d3d11_shader_cache_support_flags); disk-cache support and hits on this exact device were not queried. A variant collection describes work to warm, not a portable GPU-binary cache that is guaranteed valid across hardware and driver changes.

**Value and limits:** plausible for a first map in a later process after preparation, and for first-use visual hitches. A completely new shader/device/driver preparation still has a cost. No shader-compile timing was found in the inspected logs; its contribution is unknown. Avoid `WarmupAllShaders` and whole-roster warmup as the default: unnecessary variants can lengthen the very wait being optimized.

### Benchmark Faster Disk Representations Selectively

**Installed finding and proposed experiment:** the custom bundle set is already LZ4HC, not LZMA. Generic LZMA-to-LZ4 conversion is therefore not an available win. Compare LZ4 with uncompressed copies only for assets actually implicated by I/O/decompression profiling. Unity supports [recompression and the three bundle storage formats](https://docs.unity3d.com/6000.0/Documentation/Manual/assetbundles-compression-format.html). More disk space only pays when decompression savings exceed the extra bytes read. The full set's block tables imply about 13.60 GiB of uncompressed content versus 4.62 GiB of installed bundle files, roughly 9 GiB more before container overhead. That is a storage scale estimate, not a recommendation to duplicate the whole set or a speedup estimate. Uncompressed is not automatically faster than LZ4 on this workload.

Caches should live on `V:` with an explicit size cap, content/version validation, and atomic publication. Keep one declared load representation; missing or invalid preparation should produce a visible diagnostic or explicit rebuild, not quietly select a second reader. Actual storage cost and speedup remain unmeasured.

Caching parsed immutable map input is a lower-priority research option. It requires a verified native consumer and independent mutable session state; no general current native map-cache handoff was established. Do not serialize and reuse live map/squad objects, or bypass native session initialization to claim a faster load.
