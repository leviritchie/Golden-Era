# RAG Chunk: olden-era-playtest/100-visual-lanes

> Archived RAG snapshot derived from the 2026-05-02 knowledge base. Use only for search context; verify every current/default/runtime claim against source and validators.
Two major visual lanes exist.

Esquire lane: `EsquirePikemanVisuals.cs` replaces `units/Humans/1Prefabs/esquire` and `esquire_map` from `custom_units_esquire`. Battle works; map is historically fog-sensitive; previews are nonworking.

HoMM3 import lane: `Homm3ImportVisuals.cs` and `homm3_import.json` drive 21 Stronghold entries from `homm3_bundles`. Each entry has battle/map paths, donor presentation/shell paths, bundle name, asset paths, a lab-folder audio stem (`audioStemPrefix` must be `HOMM3_<homm3_lab sid>_`, not faction-keyed), and game unit SIDs.

Stronghold battle billboard feet alignment has two knobs that should stay in sync: live runtime config `esquirePikemanBattleBillboardExtraY=0.06` and Unity authoring preset `battleQuadLocalPositionExtraY=0.06` for Stronghold `tools/homm3_import/presets/*/authoring.json`. The runtime key is shared with the Esquire lane, but live config disables Esquire visuals. If future bundle rebuilds or config resets make feet clip into the battlefield again, check these values before changing materials or pivots.

Tears of Ashan alternate-upgrade visuals are implemented as seven dedicated `custom_units_toa_*` bundles and the seven `_upg_alt` entries in `homm3_import.json` point at those bundles. The real local ToA asset source is `vcmi/Mods/tears-of-ashan/content.zip`; do not use loose `vcmi/Mods/third-upgrades/` as the primary source even though many Stronghold files are byte-identical. ToA Stronghold battle/map DEFs and icons live under `sprites/creatures/stronghold/...` inside the zip. Tier 2 is special: ToA maps the alternate to `core:boar`, ships Stronghold map/icon overrides, but has no `sprites/creatures/stronghold/battle/lvl2Alt.def`; the local `toa_boar_rider` bundle uses the core neutral Boar battle DEF and ToA map DEF. See `docs/homm3_stronghold_toa_visual_findings.md`.

HoMM3 unit previews are separate from battle/map. When preview hooks are enabled, `Homm3ImportPreviewSyntheticMeshHook` discovers the five-parameter preview loader by signature across relevant game assemblies. Names such as `cld.sgk` and `clu.spo` are build-specific historical observations, not current owner contracts. Historical warning: do not re-enable broad reflected `Homm3ImportClbPreviewFactoriesHook` registration from `Homm3ImportUnitPreviewModelHook`; on May 2, 2026 post-processing shared `BhUnitPreviews.hqv/hqr` `clb` rigs matched the right-side adventure HUD hero/town button disappearance after city/recruitment UI use. For Golden Era, `clb` is stale: current preview wrappers should resolve through `GameSymbols.UnitPreview.PreviewWrapperTypeNames` / semantic accessors, and the legacy `Homm3ImportClbPreviewFactoriesHook` stays outside `OFFICIAL_DEOBF_BUILD`. The safer path is synthetic `cld.sgk` supply plus explicit `BhUnitWindowPreview` factory/`Show` post-processing. Do not re-enable the narrow `BhUnitPreviews.hqr` recruitment replacement unless a true per-tile anchor is found: May 3 logs showed it uses one shared world-space preview point, so replacement sprites render behind/around the whole recruitment window. Do not refuse layer-0 `cld.sgk` requests: that made all previews black and caused `BhUnitWindowPreview` NREs, proving the detail preview path can still require those supplied prefabs. If recruitment/upgrade city UI needs suppression, use a narrow call-stack discriminator (`BhHireUnit*` / city upgrade unit frames), not layer or parent name, and satisfy the loader with an empty placeholder instead of falling through. Release warning: as of `0.1.256`, the release full-feature slice must respect `homm3ImportPreviewHooks=false`; forcing preview hooks on caused live Steam `BhUnitWindowPreview.beri` / `Show` NREs. Keep release detail-preview replacement opt-in until the current wrapper path is statically remapped. `cld` is obfuscated and may not live in the same assembly as `ObjCityConfig`; scan relevant loaded game assemblies and match `sgk` by parameter shape, not by an exact `:bool` return. If the hook still misses, use its reflected `sgk candidates=` warning.

If the preview background/circle appears but the HoMM3 sprite does not, the loader is probably fixed and the remaining problem is billboard render visibility. Do not solve this by scoring `Camera.allCameras` / `WorldToViewportPoint` / `targetTexture` in `Homm3BattleBillboardCameraFacing.LateUpdate`; that crashed in `coreclr.dll` on May 2, 2026. Preview windows should not attach the dynamic camera-facing component. Prefer safe renderer fixes, such as cloning preview materials and setting culling off for the flat HoMM3 quad.

Preview targets default to `Sprites/Default` in `Homm3PreviewFineTuneRegistry`, not the battlefield `Hex/Lit` material. If material/texture binding is proven but the preview sprite is still absent, compare `Homm3Import unit preview custom(after presentation)` renderer `boundsCenter`, `boundsSize`, `visible`, `sort`, and `rq` diagnostics against the preview-window background bounds before changing placement or render order. May 2, 2026 logs showed the custom quad active/visible with texture bound and preview-only overlay state applied (`renderQueue=4000`, high renderer sorting order). Exact depth alignment put the quad on the background plane around `z=-9.85` and still rendered invisible; offsetting slightly toward negative Z also stayed invisible. Do not parent the fitted billboard to the background transform: that made it disappear. Detaching the model from `Rotatable` to the legacy `clb` preview root also made it invisible even though logs still showed active/visible renderers. The last partially visible state kept the model under `Rotatable`, fitted bounds to the background, and became visible only after manually spinning the preview; current experiments should preserve that render space and test stable facing/orientation changes there. Commit `bc9e7d5` tried a blind yaw+180 flip and still showed no sprite. A first production attempt mapped "leftmost" to orbit160, but it landed far right and required rotation. Orbit200 was near center but made the quad thin because orbit rotated its orientation too; orbit205 was visible but barely right of center. Single detail previews now use `PreviewCalibrationEnabled=false`, position-only orbit207, scale 1.25, and slot `(0, -0.12, 0)` so the billboard stays broadside. Do not apply that world-space placement to `BhUnitPreviews` recruitment previews because logs showed every tile sharing the same `platform`/`background` world point; local-only replacements still render as large/shared sprites behind the recruitment window. Recruitment needs a UI image/portrait hook or a discovered per-tile anchor, not 3D preview-wrapper replacement.

Battle, map, tooltip portrait, army strip portrait, unit preview, hero portrait, town, and SFX are independent surfaces. Do not assume fixing one fixes the others.

Release battle billboard left/right anchoring: HoMM3 battle frame PNGs are full DEF sheets with asymmetric transparent padding and centered Unity texture pivots. `battleQuadLocalPositionX` is part of the authored anchor for the unmirrored sheet. If `billboard/quad.localScale.x` is made negative for enemy side or temporary backward movement, mirror `billboard/quad.localPosition.x` from the same absolute authored X. Do not use renderer-bounds center preservation here; that older approach caused full-hex lateral jumps.

Release backwards attack facing: user testing on May 12 confirmed the stable route is to let vanilla own root turn-around, and the May 18 Steam interop check showed the current slots moved again. `Homm3ImportReleaseBattleVisualHook` must keep the native placement model intact, write current ecd-specific visual slots `cfam`/`cfai`/`cfar`, preserve current `ecz` movement `cfkq`/`cfkr` as native-owned, and redirect only current `ecz` orientation `cfks`/`cfkt` to the HoMM3 instance. Writing the movement pair to the HoMM3 visual root can promote a child visual offset into the native movement root and push sprites far left. Do not revive the old `ecd.bbvb(object,BattleEventArgs)` target-facing override or call `Homm3BattleBillboardCameraFacing.TryApplyTargetFacing` from attack playback; it fights vanilla facing once the orientation transform is synchronized.

Release backwards attack frame groups: use `BhBattleTimelineHelper.bbtg`/`bbue(Unit attacker, Unit target, ecd attackerDrawer, ecd targetDrawer)` only to feed target position into `Homm3BattleDiskTextureRemap.TryApplyAttackDirection`. The timeline drawer root can still be the native donor object; resolve the child HoMM3 `battle` root before checking billboard/remap helpers. Unity authoring now chooses the generated `14.Attack` family from source DEF groups: shooter groups 14/15/16 are preferred when present, otherwise melee groups 11/12/13 are used. The live `homm3_frame_NNN` index is timing only; runtime remaps up/front/down within the selected family by screen-space target angle during the short attack window. Root facing and mirroring should remain vanilla-owned through current `ecz` orientation transform `cfkt` or the historical `cfjt`.

Release battle target roots: `Unit.chds` returns `emg`, whose interface only exposes animation controls. The root/transform lives on concrete base `ecz`; in the May 6 dump, `cfib` is at 0x10, `cfic` at 0x18, and `cfid` at 0x20. If reflection or the generated interop wrapper cannot expose those members, read the IL2CPP object-reference offsets directly and wrap them as Unity `GameObject`/`Transform`. For attacker `ecd` views, prefer `cexw` first because that is the replacement billboard root; the `ecz` base root may be a vanilla object without the HoMM3 facing component.
