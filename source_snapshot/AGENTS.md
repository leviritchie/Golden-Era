## Operating Rules

- Cross-tool coordination is owned by `tools/cross_agent_manager/manager.py`, `docs/cross_agent_manager.md`, and `.agents/skills/cross-agent-manager/SKILL.md`. Codex, Claude, and other participating agents in the same checkout must use that shared board/messages for opted-in cross-tool work, claim write scopes before edits, and record decisions/evidence in versioned handoffs. Registrations do not launch agents; claims do not enforce filesystem permissions. No automatic stale-owner takeover or authorization to resume frozen lanes. Gate: `tools/validate_cross_agent_manager_contract.py` (full build tier).
- GPT-6 Astra instruction handling: the user's explicit instructions take precedence over skill and repository guidelines. Treat action-oriented requests such as "can you", "help me", and "I want to" as authorization to do the reversible work, and persist through implementation, verification, and the requested handoff instead of stopping at acknowledgement or an outline. Before asking a clarifying question or approval question, complete the already-authorized work needed to produce a concrete, reviewable result. Ask only when the missing answer can materially change the outcome or the next action is destructive, irreversible, external, or otherwise requires explicit approval. If a skill or instruction file causes a pause, approval request, or divergence from the user's intent, identify the exact `SKILL.md` or instruction and distinguish its explicit requirement from your interpretation.
- For work that can be parallelized, delegate bounded research, file inspection, or implementation checks through collaboration tools when doing so can save time or improve quality. Keep delegation messages legible, and retain ownership of the final integration, validation, and user-facing result.
- Match verification to risk: do not add tests that merely mirror a reversible, low-impact implementation. Run the focused checks required by the change, then broaden testing only for new changes, failures, or unresolved concerns. Never claim completion from a changed string or passing syntax check alone when behavior or delivery proof is required.
- One problem gets one solution. Do not add silent fallbacks unless the user explicitly asks for them.
- Prefer fail-closed behavior with clear diagnostics over permissive recovery that can hide the real fault.
- Keep obfuscated IL2CPP names centralized in `GameSymbols.cs` or the established resolver layer. Do not scatter generated names through feature code.
- Exact value reads in the Bulwark rune adapter use `GameMemberValueReader`: expected member-kind misses are quiet, but getter failures stop the read and retain a diagnostic. Gate: `tools/validate_game_member_value_reader_contract.py --run-fixture` in the full build tier. Fixture/build proof does not prove live IL2CPP read behavior.
- Adventure-map terrain lookups are replaced from the current compacted material table on every map scope, including stock-only transitions; never retain prior-map custom slot entries. Owner/proof: `docs/homm3_terrain_map_transition.md`; gate: `tools/validate_homm3_custom_biome_runtime_contract.py` in the full build tier. Runtime fix verification is pending.
- Before keying or looking up a dictionary/plan from a Harmony hook arg, pin the **live arg type** against the **map key type** (GameSymbols hints). Example: `Unit.Init` arg[2] is the battle-side wrapper (live `ObjectPublicPrcgObPrcgInTrPrcgInUnique`; pin via `BattleUnitInit.SideTypeHints` — legacy short names like `eir` are aliases only), not `TransferSide`; bridge via `BattleSideTransferSideMembers` before `TransferSide`-keyed lookup. A silent `TryGetValue` miss with a non-empty map is a failed check, not “no plan.” After types match, do **not** key Il2Cpp objects by managed `GetHashCode` / `ReferenceEquals` — separately marshaled proxies of the same native object diverge; use `Homm3DirectStateIdentity` (native pointer) or equivalent. Native-pointer keys fix managed re-wrap; they do **not** prove store and retrieve are the same object — distinct CapLog `nativeKey`s mean different objects / wrong ownership key. When a producer fills a plan/register and a later hook consumes it, keep that state until every consumer has run (or own apply on one shared registration surface); do not clear in an earlier postfix than apply — planned≠applied with quiet miss logs is **timing/ownership**, not key identity. `BattleLogic.Init` also runs during adventure-map / session `Loader` paths — fail-closed throws from optional pilots in an Init prefix can brick map load; soft-skip / log there instead. Broader class (type/bridge mismatch, managed-proxy≠native identity, enumeration, proof bar, SID misreads, producer→consumer windows): hub **Silent miss / wrong proof**.
- If a requested change would violate good engineering practice, state the professional path and risk first; proceed with the unsafe path only if the user explicitly insists.
- Preserve user and other-agent work. Do not revert unrelated changes, and do not run destructive git commands unless explicitly requested.
- After a meaningful scoped milestone is ready, create a git commit without asking first. Do not wait for the user to approve ordinary commits; still avoid force-push, amend of others' commits, secrets, and unrelated file dumps.
- When multiple tasks or temporary fact-gathering branches are in scope, consider delegating bounded research to subagents to preserve context.
- Prefer PowerShell for local searches when practical; use targeted searches rather than broad recursive scans over artifacts.
- Keep terminal commands fast and bounded: always pass an explicit `timeout_ms` on anything that could run long (builds, Unity batch, validators); never run broad recursive scans over `V:\homm3_unity_work\Assets` or other large trees (they hang); use forward-slash paths for `ls`/`cat` on junctioned paths; give read-only git commands `--no-pager`. If a command hangs, prefer a narrower, targeted replacement over retrying the same invocation.
- **Performance is a requirement, including in early testing (user policy 2026-10-02).** The project keeps getting stuck in validation hell, with gates, checks and slow pipelines blocking it for hours. Treat wall-clock time, GPU/CPU use and RAM/VRAM footprint as first-class acceptance criteria, not polish for later. Concretely:
  - Measure before you add. Every new gate, validator, certificate or pipeline stage states its runtime and peak RAM/VRAM in its doc or report. A step that takes more than a few minutes needs a reason and an incremental or cached path.
  - Do only the work that changed. Prefer hashing, caching and incremental checks over re-running whole suites; for example, don't re-validate every installed town to install one. Expensive tiers (full pose certificates, extra poses, full validation) stay opt-in and are named as such.
  - Resource gates must be able to pass. Size waits from measured peaks against the real machine (a 16 GB GPU with about 2.4 GB held by the desktop; a host limited to about 52 GB of commit). A gate that can never be satisfied is a deadlock, and it must fail fast with a diagnostic instead of holding locks for hours.
  - No idle polling. Use background completion notifications or long intervals, and never hold a shared lock (GPU, RAM ticket, deploy slot) while waiting on something else.
  - Speed fixes keep correctness. Don't make things faster by quietly relaxing a quality gate. Make the check itself cheaper (GPU, vectorised, incremental), or raise the trade-off with the user.
- **GPU first (user policy 2026-10-01).** Any technique that can run on the GPU must use it: rasters, ray casts, per-pixel/per-texel/per-face array math, image filtering, fitting/optimisation. Use torch CUDA / moderngl; reuse `tools/homm3_town_scene_meshes/town_gpu_kernels.py` (`docs/town_gpu_kernels.md`). Keep a `--device cpu` reference with a parity test; a missing GPU fails clearly, with no silent fallback. CPU is acceptable only for inherently sequential steps (e.g. union-find labelling) or I/O, and the reason must be stated in code or report.
- Avoid writing large files to `C:`. Prefer repo-local or `V:` paths when a temporary artifact is genuinely needed.
- **Scratch cleanup.** Put scratch for a lane under one folder, `V:\olden_port_work\<lane>\`. When the lane hands back, delete that folder's superseded outputs, keeping only what the report cites. A rejected candidate keeps its stage JSON/reports and drops its meshes, renders and bundles.
- **Cold-data offload.** Data that is not read by any active pipeline (checked by dependency trace, never by size or age alone) goes to iCloud through `V:\olden_port_work\cold_offload_sweep.py sweep` (`--dry-run` first). It runs the trace and archives large sets (7-Zip volumes plus a sha256 manifest, verified before any source is removed), then calls `icloud_offload.ps1` with all sources in one call. Never offload secrets, `.git`, or git-tracked files. Restore: `docs/icloud_offload_restore.md`.
- **In-game checks.** Every installed change that needs the user's eyes gets a row in `docs/ingame_check_queue.md`. That doc is the one queue; do not keep a parallel list in reports.

## Build, Deploy, And Validation

- New contracts must have validators wired into the build/deploy path that would fail if a future agent violates the contract. Since 2026-10-01 the plugin build is tiered (`docs/build_validation_tiers.md`): the default test-deploy tier runs only compile plus deploy-safety gates, and contract validators run under `-p:FullValidation=true`. Gate new validators on `FullValidationNormalized`, and run the full tier (or the owning validator) before releases and when touching a contract. A quick build does not prove contracts.
- For Golden Era compile checks, use the established OfficialDeobf/Golden-Era build path rather than ad hoc assembly references. A plain build can hide drift against live interop.
- The OfficialDeobf build compiles against interop that is not the live game's. `ValidatePluginLiveInteropRefs` (`tools/verify_plugin_live_interop_refs`, post-build, before deploy) resolves every plugin TypeRef/MemberRef, and one level of the called interop wrappers' IL, against `<Golden Era>/BepInEx/interop`; new unresolved refs fail the build. Pre-existing gaps live in its `allowlist.txt`: remove lines as they are fixed, never add one to pass. Read deobf-only members (`me`, `get_id`, and similar) by reflection through `GameSymbols.cs`.
- Unity batch jobs: agents must submit, not launch. Use the Unity queue runner (`tools/unity_queue/unity_queue.py`, `docs/unity_queue_runner.md`; gate `tools/validate_unity_queue_contract.py`), which batches jobs per project into one editor launch and fails closed. `--unity-direct` is the only, explicit bypass.
- HoMM3 `homm3_bundles` deploy is opt-in. Normal plugin deploys must not copy `tools\homm3_import\build_out\custom_units_*`; explicit `DeployHomm3Bundles=true` deploys must pass the payload-directory validator first.
- Before claiming readiness for Steam or Golden Era port work, run the repo's obfuscated-symbol and direct-interop audits when the touched code could introduce raw generated references.
- Keep significant milestones committed in git when the work is ready and scoped.

## Runtime And Decomp Workflow

When runtime proof or a modding bridge is relevant, test in this order:

1. Native live bridge features.
2. Live bridge volatile features.
3. General-purpose bridge enhancement that helps future analogous work.
4. Manual build/deploy diagnostic only after the above routes fail.

Use the `decomp-search` skill whenever there is a branching technical choice in HoMM Olden Era modding work. Prefer native-friendly modding solutions over quick patches.

If a change breaks behavior during debugging, do not revert and retest merely to produce no new signal; either continue toward a forward fix or choose a new path after reverting.
